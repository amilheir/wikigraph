01  the thesis

The graph is a filter, not a footnote.

Most RAG retrieves chunks by raw cosine similarity and hopes the right ones float up. That blurs namesakes — “Tesla” the company and the inventor sit close in vector space. WikiGraph runs graph-first: it scores the question against entity vectors, keeps the dominant sense, and restricts the chunk search to that sense’s documents. The vector layer never sees the rival meaning.

▲ graph layer

resolve the meaning

Embed the question, compare it to every Entity.descVector, and keep the entities within a cosine margin of the best one. Their documents become the scope.

operations.py · knowledgeOperation.searchEntities()

● vector layer

read the evidence

Embed the same question, compare it to Chunk.chunkVector — but only for chunks inside the scoped documents — and return the top K passages as evidence.

03  stage by stage

The six steps, against the code.

Everything below lives in knowledgeOperation.onSearch() in operations.py, called synchronously by chatProcess for every question.

1

Match the entities — by vector and by name

The question is embedded once and compared to every entity’s description vector; entities at or above entityFloor (0.30) are considered “about” it. In parallel, any entity whose full name literally appears in the question is matched too (nameMatch) — so an explicitly-named entity that embeds weakly (e.g. one of three astronauts in a list) is never lost.

SELECT TOP 8 e.%ID, …, VECTOR_COSINE(e.descVector, EMBEDDING(?,'wikiembed')) AS score FROM GraphKB.Entity e WHERE e.lang = ? AND e.descVector IS NOT NULL ORDER BY score DESC -- plus: WHERE UPPER(?) LIKE ('%' || UPPER(e.entityName) || '%') (lexical name match)
2

Keep only the winning sense

Rows are already ordered by score, so the cutoff is topScore − scopeMargin (0.12). Entities within that band are “in scope”; a dominant match excludes its namesake. A tight margin means one sense wins; a wider margin lets co-relevant senses through.

cutoff = matched[0].score − scopeMargin inScope = [ e for e in matched if e.score ≥ cutoff ]
3

Collect their documents

Each in-scope entity carries a documentRef back to the article it came from. The distinct set of those ids becomes the scope — the bridge handed to the vector lane.

4

Search chunks — two ways, then merge

Two cosine searches over Chunk.chunkVector run and are merged (dedup, best score, capped at maxChunks):

(a) document-scoped — confined to the winning sense’s articles via documentRef IN (scopeDocs), top searchTopK (5). (b) per-entity — for each matched/named entity, its top perEntityChunks chunks among those that mention it (EntityMention), so every named entity contributes evidence from whatever article actually describes it.

(b) … VECTOR_COSINE(c.chunkVector, EMBEDDING(?,'wikiembed')) AS score FROM GraphKB.Chunk c JOIN GraphKB.EntityMention em ON em.chunkRef = c.%ID WHERE em.entityRef = ? ORDER BY score DESC
5

Widen if the scope was too tight

Over-narrow scoping can starve recall — and the upstream “do I need to learn?” decision with it. If the best scoped chunk is below scopeFloor (0.45), the search re-runs across all documents and keeps whichever result is stronger.

6

Expand the graph, then merge

A 1-hop walk over GraphKB.Relationship among the matched entities adds typed facts (source → predicate → target). Chunks, entities and relationships are packed into one JSON context; bestScore is returned so chatProcess can decide whether to answer or to learn.

04  the substrate

Both searches run inside IRIS.

There is no external vector store. Text becomes vectors through the IRIS EMBEDDING datatype (config wikiembed) backed by %Embedding.OpenAI pointed at Ollama’s /v1/embeddings — so every EMBEDDING() is a fast HTTP call, not an in-process model load. Similarity is VECTOR_COSINE over HNSW indexes.

GraphKB.Entity

descVector drives the graph lane. Deduped on name + type + lang so senses stay separate; documentRef ties each to its article. HNSW + cosine.

GraphKB.Chunk

chunkVector drives the vector lane. It embeds embedText — the passage prefixed with the article title — which separates senses in vector space; chunkText stays clean for display.

GraphKB.Relationship · EntityMention

Relationship = typed edges (1-hop expansion enriches context). EntityMention links each entity to the chunks that mention it — the bridge the per-entity search follows to pull evidence across documents.

EMBEDDING · wikiembed

%Embedding.OpenAI → Ollama, 1024-dim. The model (harrier-0.6b, multilingual) is configurable via EMBEDDING_MODEL; bge-m3 also fits.

VECTOR_COSINE · HNSW

Both lanes use the same operator and the same query vector — only the row set differs. HNSW indexes (Distance='Cosine') keep the search fast as the graph grows.

chatProcess

Owns the loop: search → (learn if weak) → re-search → answer, writing pending→searching→learning→answering→done so the UI can follow along.
