02 the link-kg strategy

One entity, not five.

An LLM spells the same character a dozen ways across an article. The naïve approach extracts each chunk blind and fragments them. LINK-KG feeds a running registry back into every extraction, so mentions resolve to one canonical node — aliases and all.

Stateless · no memory

Each chunk on its own

03 the registry loop

Memory that rides with the extraction.

Inside ingestProcess, a per-article registry is built across the chunk loop: it's injected into each extraction prompt (KNOWN_ENTITIES_PROMPT), and storeGraph writes new canonical names back into it for the next chunk.

04 the backstop

And a sweep to reconcile the rest.

LINK-KG prevents fragmentation within an article. Across articles, a separate resolution pass reuses the same vectors and aliases to merge what's left — name-driven, gated by description similarity, so namesakes stay apart.

Prevention + cure

The registry keeps each page clean as it's read; the resolution pass periodically blocks candidates by description-vector neighbours, matches on name, and merges each cluster into its fullest name — folding the rest into aliases.

LeiaPrincess LeiaLeia Organa →Princess Leia Organa

…but never over-merge

A shared name only merges when the descriptions agree — so two genuinely different things stay distinct.
