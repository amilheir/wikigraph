WikiGraph

A chatbot whose knowledge grows by itself. Ask it anything — if the answer isn’t in its graph yet, it reads the one matching Wikipedia page, turns it into vectors and a web of entities, and answers from there. Everything lives in IRIS.

self-growing one page, no link-following graph-first retrieval EN / PT everything lives in IRIS

01 the idea

Knowledge it doesn’t have, it goes and learns.

A normal RAG bot can only answer from what was loaded up front. WikiGraph closes the loop: a question it can’t answer well becomes a trigger to read, structure, and remember — so the second time, it’s instant.

01

ask

A question arrives in English or Portuguese through the chat UI.

02

search

It resolves the question to known entities and runs a graph-first vector search over what it already has.

03

learn

If the score is too low it fetches a single Wikipedia page — never its links — and builds the graph from it.

04

answer

A local LLM replies using only that graph — concise, grounded, in the question’s language.

02 architecture

Two containers. One of them does almost everything.

The browser talks to a Flask app hosted inside IRIS over WSGI. It only writes a pending row; a polling service picks it up and an interoperability production — written in Python with pyprod — runs the whole pipeline. Ollama serves both the chat model and the embedding model.

service & orchestration business operations & processes data & external services

03 the request lifecycle

A status the frontend watches.

Each chat row carries a status. The UI polls GET /api/chat/<id> and shows a live bubble — including a 📚 “learning…” state while IRIS reads Wikipedia. Every hop is also a traceable interoperability message.

phase 00

pending

The WSGI app inserted the row; the polling chatService is about to claim it.

phase 01

searching

Resolves the question to entities, then scopes the chunk vector search to their documents.

phase 02

learning

Score below 0.55 → fetch the best page, chunk, embed, extract the entity graph.

phase 03

answering

The LLM writes a grounded reply from the retrieved chunks and triples.

phase 04

done

The answer lands; the topic is now remembered for next time.

04 graph-first retrieval

Let the graph pick the right sense.

A plain vector search blurs namesakes together. knowledgeOperation matches the query against entity description vectors first — and by name, when an entity’s full name appears in the question. Only entities within a cosine margin of the top match contribute their documents, and the chunk search is scoped to those documents, gathering chunks per entity through EntityMention so every named entity keeps its evidence. A weak scope widens to everything, then one hop over relationships joins related facts. Learning is disambiguated the same way.

scoping · scopeMargin 0.12

“Tell me about Tesla, the car company”

The company entity outscores the inventor by more than the margin, so only its document is in scope — chunks about Nikola Tesla never enter the context. If the best scoped chunk is weak (< 0.45) the search widens to protect recall.

disambiguation · candidate rerank

“Who was Neil Armstrong?”

When learning, the LLM distils a clean search title, several Wikipedia candidates are fetched, and the one whose intro best matches the question (by cosine) is ingested — the astronaut, not RV Neil Armstrong the research ship.

05 the knowledge base

A graph of meaning, stored entirely in IRIS.

No external vector store, queue, or cache. Text becomes vectors via the IRIS EMBEDDING datatype; similarity is VECTOR_COSINE over HNSW indexes; entities and relationships form the graph traversed during retrieval.

GraphKB.Document

One row per ingested page, unique by pageId + language — an already-known topic skips learning and answers fast.

GraphKB.Chunk

Passages of an article. chunkVector embeds embedText — the chunk prefixed with its article title — over an HNSW index; chunkText stays clean for display.

GraphKB.Entity

People, places and concepts the LLM pulls from each chunk, each with a description vector. Identity is the canonical name (deduped on name + language; the LLM’s type is a normalized attribute, not part of identity); alternate forms live in aliases (LINK-KG).

GraphKB.Relationship

Typed edges source → predicate → target. After the entity match, the search expands one hop across these for richer context.

GraphKB.EntityMention

Links an entity to every chunk that mentions it — the bridge the per-entity search follows so a named entity contributes evidence from whatever document describes it, even across articles.

GraphKB.ChatRequest

The chat state machine itself — question, language, status, detail and answer — inserted by the web app and polled by the UI.

06 keeping the graph clean

One entity, not five.

LLM extraction is noisy — it spells the same character five ways and mislabels its type. WikiGraph fights fragmentation twice: prevention while reading, and a cure that runs after.

prevention · LINK-KG

Coreference-aware extraction

Each chunk is given the canonical entities found earlier in the same article, so the LLM reuses an established name instead of inventing variants. It returns a full canonical name + aliases + a normalized type. Identity is the name, not the unreliable type — so R2-D2 (Droid) and R2-D2 (Droide) are one node. Guards drop an alias that’s really another entity, and tidy LOCATION/Location/Object → Location.

cure · resolutionOperation

The resolution pass

A background sweep, per language, from Manage knowledge (Preview / Merge) or POST /api/resolve. Block by description cosine (HNSW), match name-first (exact / token-containment / fuzzy, gated by description agreement so the two Teslas stay apart), then merge each cluster into the most complete name — Leia · Princess Leia · Leia Organa → Princess Leia Organa — repointing mentions & relationships. It also scrubs noisy aliases and normalizes types. dryRun previews every proposed merge before anything is written.

09 tuning

Every dial, and where to set it.

Each parameter below is a live setting in the Management Portal (Interoperability → Productions → the item → Settings) — change it without recompiling. The cosine thresholds are calibrated for the current embedding model (harrier-0.6b / bge-m3, 1024-dim); ingestProcess settings affect future ingestions only.
